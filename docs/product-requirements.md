# Narrative Tracker

## 产品需求文档 v2.0

文档定位：这是 Narrative Tracker 的产品需求文档。核心方向是：去掉服务器、去掉被动监控、去掉第三方 App 数据采集，把产品定义为一个本地运行、用户主动提交事实、用 AI 辅助自我认知校准的强隐私工具。

---

## 1. 产品定义

### 1.1 一句话描述

Narrative Tracker 是一个帮助年轻人用自己提交的事实，校准自我认知的本地 AI 工具。

### 1.2 产品使命

帮助年轻人更诚实、更温和地认识自己。

很多年轻人并不是故意欺骗自己，而是缺少稳定的反馈系统。他们会说：

- 我很自律。
- 我最近很努力。
- 我不擅长社交。
- 我总是拖延。
- 我压力太大，所以什么都做不了。

这些说法可能是真的，也可能只是长期形成的自我叙事。Narrative Tracker 不负责审判用户，也不偷偷监控用户，而是基于用户自己主动提交的事实，帮助用户看见：

- 我认为的自己是什么样？
- 我最近真实做了什么？
- 两者之间是否一致？
- 如果不一致，差距在哪里？

### 1.3 产品原则

#### 原则一：不监控用户

App 不截屏，不读取其他 App 数据，不读取屏幕时间，不读取位置，不读取通讯录，不读取财务数据，不做后台行为监控。

如果一个功能需要偷偷观察用户，它就不应该进入这个产品。

#### 原则二：所有事实由用户主动提交

产品只分析用户主动输入、主动选择、主动保存的内容。

用户提交事实，不是为了被评判，而是为了让自己拥有更清晰的反馈。

#### 原则三：数据只属于用户

第一版不做服务器，不做账号系统，不做云数据库，不上传用户隐私数据。

所有叙事、事实、分析结果都保存在用户设备本地。

#### 原则四：AI 是镜子，不是裁判

AI 的作用是帮助用户整理事实、发现模式、提出可能的偏差。AI 不应该用诊断、审判、羞辱、命令式语言。

产品语气应该像一个冷静、温和、有证据意识的教练。

#### 原则五：开源建立信任

作为强隐私产品，开源不是附加项，而是产品策略。用户应该能够验证：

- App 没有上传隐私数据。
- App 没有隐藏的监控行为。
- API Key 没有被保存到开发者服务器。
- 分析逻辑是透明的。

对一个 18 岁的创作者来说，一个认真维护的开源项目本身也是非常有价值的作品集。

## 2. 目标用户

### 2.1 第一批用户

第一版不面向所有人，而是面向愿意自我反思的年轻人：

- 高中生和大学生
- 刚进入职场的年轻人
- 对拖延、自律、学习效率、社交焦虑有困扰的人
- 喜欢日记、复盘、心理学、AI 工具的人
- 愿意每隔几天提交事实并查看反馈的人

### 2.2 首个核心场景

第一版建议聚焦在学习、行动、自律和拖延，不要一开始覆盖人生的所有方面。

核心问题可以是：

> 我以为我是什么样的人？我最近的事实是否支持这个判断？

示例：

- 我以为自己很努力，但事实是否支持？
- 我以为自己总是拖延，但事实是否真的如此？
- 我以为自己不自律，但有没有被我忽略的进步？
- 我以为自己很忙，但事实中真正完成了什么？

## 3. 核心产品循环

### 3.1 第一次打开 App

用户完成一次初始自我画像。

App 询问用户如何看待自己，形成第一版 self narrative。

示例问题：

- 你觉得自己是一个自律的人吗？1-10 分。
- 你觉得自己最近学习或工作的投入度如何？1-10 分。
- 你觉得自己拖延严重吗？1-10 分。
- 你觉得自己能坚持长期目标吗？1-10 分。
- 你觉得自己最近最大的优势是什么？
- 你觉得自己最近最想改变的问题是什么？
- 用三个词描述现在的自己。

这一步的目标不是得到准确答案，而是保存用户“认为自己是什么样”的基准。

### 3.2 每次打开 App

用户提交事实，而不是只提交感受。

示例问题：

- 今天你实际完成了什么？
- 今天你原本计划做但没有做的事情是什么？
- 今天有没有一件事证明你在靠近目标？
- 今天有没有一次明显的逃避？
- 今天最能代表你真实状态的事实是什么？
- 如果只能写一句事实，你会写什么？

事实输入应该很轻，最好 30-60 秒内完成。

### 3.3 用户选择查看反馈

提交事实后，用户可以选择是否查看分析。

App 对比：

- 初始自我评价
- 最近事实记录
- 最近用户自己的复盘
- AI 生成的模式总结

输出：

- 一致的地方
- 不一致的地方
- 可能被低估的地方
- 可能被高估的地方
- 证据不足的地方

产品必须允许“不分析”。用户拥有查看反馈的主动权。

## 4. MVP 功能范围

### 4.1 V1 必须做

#### 本地自我画像

- 初次打开 App 时完成自我评价
- 支持 1-10 分量表
- 支持短文本回答
- 支持后续重新评价
- 保存历史版本

#### 本地事实日志

- 用户每次打开 App 时提交事实
- 支持每日事实、计划落差、行动证据、逃避事件
- 支持自由文本
- 支持少量结构化标签，例如学习、健康、社交、情绪、拖延

#### 差距反馈

- 对比“我认为的自己”和“我提交的事实”
- 生成简短反馈
- 给出差距等级，例如低、中、高
- 必须展示证据来源
- 必须支持“证据不足”

#### 用户自带 AI Key

- 用户在设置中填写自己的 AI API Key
- App 直接从用户设备调用 AI 服务
- 开发者不提供服务器转发
- 开发者不保存用户 API Key
- API Key 保存在系统安全存储中，例如 iOS Keychain、Android Keystore

#### 本地存储

- 所有数据保存在本机
- 不需要登录
- 不需要服务器
- 不需要云数据库
- 支持本地导出
- 支持一键删除所有数据

#### 内购

通过 App Store 和 Google Play 做内购。

建议分层：

- Free：可查看最近 3 天反馈
- Plus：可查看最近 1 个月反馈
- Pro：可查看最近 1 年反馈

付费解锁的是本地历史范围和分析能力，不是云服务。

#### 开源

- 客户端代码开源
- 隐私策略公开
- 数据流说明公开
- AI 请求流程公开
- 不包含用户隐私数据收集逻辑

### 4.2 V1 不做

- 不做服务器
- 不做账号系统
- 不做云同步
- 不做社交功能
- 不做排行榜
- 不做团队版
- 不做心理诊断
- 不做治疗建议
- 不读取屏幕时间
- 不读取其他 App 数据
- 不读取通讯录
- 不读取位置
- 不读取财务数据
- 不自动截屏
- 不做后台监控

## 5. 反馈设计

### 5.1 反馈必须基于证据

每条反馈都应该引用用户自己提交过的事实。

错误示例：

> 你其实并不自律。

正确示例：

> 你给自己的自律评分是 8/10。过去 7 天里，你提交了 5 条计划，其中 2 条完成，2 条部分完成，1 条没有开始。所以目前事实更支持“你有行动意愿，但执行稳定性还不够”。

### 5.2 反馈必须允许不确定

产品不能为了显得聪明而强行下结论。

当数据不足时，应该明确说：

> 目前事实记录还太少，不能判断你是否真的拖延。建议再记录 3 天。

### 5.3 反馈语气

推荐语气：

- 温和
- 具体
- 基于事实
- 不羞辱
- 不命令
- 不诊断

禁止语气：

- 你错了
- 你在骗自己
- 你有问题
- 你必须改变
- 你就是不自律

内部可以保留“量化你对自己说的谎”作为锋利定位，但用户界面应使用更温和的表达：

> 看见你以为的自己，和你真实行动之间的距离。

## 6. AI 分析逻辑

### 6.1 输入给 AI 的内容

AI 只接收用户主动提交的内容：

- 用户自我画像
- 用户事实日志
- 用户选择的时间范围
- 用户请求分析的主题

AI 不接收：

- 后台采集数据
- 其他 App 数据
- 屏幕截图
- 位置轨迹
- 通讯录
- 财务信息

### 6.2 AI 输出格式

建议输出结构：

```json
{
  "summary": "一句话总结",
  "alignment_score": 72,
  "confidence": "medium",
  "matched_beliefs": [
    {
      "belief": "我最近很努力",
      "evidence": "过去 7 天提交了 5 条学习事实，其中 4 条与目标有关",
      "assessment": "基本一致"
    }
  ],
  "gaps": [
    {
      "belief": "我很自律",
      "evidence": "多次提到计划开始时间被推迟",
      "assessment": "执行稳定性不足"
    }
  ],
  "insufficient_evidence": [
    "目前无法判断社交状态，因为缺少相关事实"
  ],
  "suggested_reflection": "下周可以重点观察计划开始时间，而不是只记录完成结果。"
}
```

### 6.3 AI 安全边界

AI 不应该：

- 做心理疾病诊断
- 给医疗建议
- 给极端人生建议
- 使用羞辱性语言
- 把用户描述成固定人格
- 在证据不足时做强判断

## 7. 数据与隐私

### 7.1 数据位置

| 数据 | 存储位置 | 是否上传到开发者服务器 |
|------|----------|----------------------|
| 自我画像 | 用户设备本地 | 否 |
| 事实日志 | 用户设备本地 | 否 |
| AI 分析结果 | 用户设备本地 | 否 |
| API Key | 系统安全存储 | 否 |
| 内购状态 | App Store / Google Play | 否 |

### 7.2 数据控制

用户必须可以：

- 查看所有本地数据
- 导出所有本地数据
- 删除所有本地数据
- 关闭 AI 分析
- 更换或删除 API Key

### 7.3 隐私承诺

建议写入产品首页或设置页：

> 我们不拥有你的数据。  
> 我们不读取你的其他 App。  
> 我们不截屏。  
> 我们不建立服务器保存你的隐私。  
> 你提交什么，App 才分析什么。

## 8. 商业模式

### 8.1 收费原则

产品不通过广告赚钱，不出售数据，不用隐私换收入。

收入只来自 App Store 和 Google Play 内购。

### 8.2 建议定价

具体价格可以后续验证，第一版可以先定义权益：

| 层级 | 权益 |
|------|------|
| Free | 最近 3 天反馈、本地记录、基础分析 |
| Plus | 最近 1 个月反馈、趋势总结、更多分析主题 |
| Pro | 最近 1 年反馈、长期叙事变化、导出年度报告 |

### 8.3 成本结构

由于 AI Key 由用户自己提供，产品方不承担 AI 推理成本。

主要成本：

- App 开发
- 开源维护
- App Store / Google Play 上架
- 文档和隐私说明维护
- 社区运营

## 9. 技术方案

### 9.1 推荐技术路线

第一版可以选择跨平台方案，以便同时支持 iOS 和 Android。

推荐候选：

- Flutter
- React Native

如果目标是尽快双端发布，Flutter 是比较适合的选择。

### 9.2 本地存储

候选方案：

- SQLite
- Drift
- Realm
- 本地 JSON 文件

建议第一版使用 SQLite 或 Flutter 生态中成熟的本地数据库方案。

### 9.3 安全存储

- iOS：Keychain
- Android：Keystore

API Key 必须保存在系统安全存储中，不能明文存在普通数据库或日志里。

### 9.4 AI Provider

第一版支持一个 AI Provider 即可，不要一开始支持太多。

可选：

- OpenAI
- Anthropic
- Gemini

建议先支持 OpenAI-compatible API 格式，后续再扩展。

### 9.5 开源仓库结构建议

```text
narrative-tracker/
  app/
  docs/
    privacy.md
    data-flow.md
    product-requirements.md
  examples/
    sample-feedback.json
  README.md
  LICENSE
```

README 第一屏应该明确：

- Local-first
- No server
- No tracking
- Bring your own AI key
- Open source

## 10. 成功指标

### 10.1 MVP 验证指标

第一阶段不要只看下载量，而要看用户是否真的持续记录。

建议指标：

- 7 日内至少提交 3 次事实的用户比例
- 用户是否主动查看差距反馈
- 用户是否认为反馈有帮助
- 用户是否愿意继续使用到第二周
- 用户是否愿意推荐给朋友

### 10.2 早期目标

在正式开发完整 App 前，建议先做小规模实验：

- 找 5-10 个同龄人
- 连续使用 2 周
- 每人至少提交 5 条事实
- 每人至少查看 2 次反馈
- 访谈他们是否觉得这个工具有帮助

如果没有人愿意持续记录，说明产品问题还没有被验证。

如果他们愿意继续第三周，说明方向值得继续。

## 12. 最大风险

### 风险一：用户不愿意持续输入事实

这是最大风险。解决方式不是加更多功能，而是把输入体验做到极轻。

### 风险二：反馈太刺耳

年轻人需要的是校准，不是羞辱。反馈必须温和、具体、可选择查看。

### 风险三：AI 结论不可靠

必须展示证据和置信度。证据不足时必须说证据不足。

### 风险四：自带 AI Key 门槛高

这会限制早期用户范围，但换来了极强隐私和低成本。第一批用户可以先面向极客、自我量化社区和 AI 工具用户。

### 风险五：内购审核和开源商业模式冲突

需要提前确认 App Store 和 Google Play 对 BYOK、本地解锁、开源客户端的审核要求。

## 13. 产品建设建议

这个想法有价值，但不要急着把它做成一个复杂平台。

你现在要证明的不是“这个 App 能不能开发”，而是：

- 年轻人是否愿意记录事实？
- 他们是否愿意看到自我认知和事实之间的差距？
- 这种反馈是否真的帮助他们更了解自己？

第一版的架构应该非常克制：

- 没有服务器
- 没有账号
- 没有云数据库
- 没有后台监控
- 没有其他 App 数据采集
- 所有数据留在用户设备上
- 用户自己决定是否调用 AI
- 代码开源，接受别人检查

这个产品真正的竞争力不是“你能拿到多少数据”，而是“用户是否相信你足够尊重他的隐私”。

如果你能把这个产品做成一个温和、可信、本地运行的自我认知镜子，它会比一个复杂但让人害怕的数据平台更有生命力。

## 14. 推荐下一步

本周不要写 App。

先完成这三件事：

1. 写出 10 个初始自我画像问题。
2. 写出 10 个每日事实提交问题。
3. 找 5 个同龄人连续记录 7 天，然后手工生成第一版反馈报告。

如果他们看完报告后愿意继续记录第二周，再开始做 App 原型。
